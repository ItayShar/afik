# 2.3 Scaling the table

I would partition the raw telemetry table by day using `recorded_at` and maintain a historical summary for each device. At one million new readings per day, an index alone cannot prevent the original query from processing an increasing amount of historical data. Partitioning makes recent data easier to access and old data easier to archive, while the summary removes the need to recalculate historical averages from every raw reading.

## Daily partitions

I would use daily range partitions with boundaries at midnight UTC. Each partition would contain approximately one million readings. These are physical partitions of one logical table, so the application would continue querying `device_telemetry_logs`.

```text
device_telemetry_logs
├── p20261028: readings from October 28
├── p20261029: readings from October 29
├── p20261030: readings from October 30
└── ...
```

For the existing MySQL `TIMESTAMP` column, the partitioning expression would be `PARTITION BY RANGE (UNIX_TIMESTAMP(recorded_at))`, with successive UTC midnight boundaries. I would verify the selected partitions using `EXPLAIN`.

I chose time-based partitioning because this query has a rolling 24-hour window and old data can be summarized by completed days. Partitioning only by device would still require reading each device's entire history for every execution. Daily partitions also provide a convenient unit for retention and archiving.

I would also retain the covering index `(device_id, recorded_at, voltage, current)` within the partitioned table. 
However, partitioning alone does not solve this query: the original calculation needs both recent and historical readings and would still visit almost all partitions.

## Historical summaries

I would maintain a `device_history_stats` table with one row per device, keyed by `device_id`, containing `power_sum` and `valid_count`. Every row would summarize readings strictly before one shared timestamp, `B`, stored in a separate summary-state record.

```text
power_sum   = SUM(voltage * current)
valid_count = COUNT(voltage * current)
```

The count includes only non-NULL power values, preserving the behavior of `AVG(voltage * current)`. For a device with no valid measurements, the stored sum and count would both be zero.

Here, `B` stands for the **summary boundary timestamp**: all readings strictly before `B` are already included in the historical summary, while readings at or after `B` must be read from the raw telemetry table. For example, if `B` is October 30 at 00:00 UTC, the summary contains readings before October 30, but none from October 30 onward. A daily background job would advance this boundary by one completed day, adding that day's per-device sums and counts to the cumulative summary. For a query evaluated today, the target boundary is midnight at the start of yesterday, ensuring `B` is no later than the rolling 24-hour cutoff. If the job is delayed, the query can still use the older boundary as long as the required raw data remains available; it will simply scan more days.

## Revised query

The application would supply three parameters using UTC consistently:

- `:as_of`: the fixed evaluation time.
- `:cutoff`: exactly 24 hours before `:as_of`.
- `:B`: the boundary associated with the summary being read, where `B <= cutoff`.

The historical average combines the cumulative summary before `B` with raw readings in `[B, cutoff)`. The recent average uses raw readings in `[cutoff, as_of)`. These intervals neither overlap nor leave a gap, preserving the exact rolling time window rather than rounding it to whole days.

```sql
WITH recent AS (
    SELECT
        device_id,
        AVG(voltage * `current`) AS recent_avg
    FROM device_telemetry_logs
    WHERE recorded_at >= :cutoff
      AND recorded_at < :as_of
    GROUP BY device_id
),
history_parts AS (
    SELECT device_id, power_sum, valid_count
    FROM device_history_stats

    UNION ALL

    SELECT
        device_id,
        COALESCE(SUM(voltage * `current`), 0) AS power_sum,
        COUNT(voltage * `current`) AS valid_count
    FROM device_telemetry_logs
    WHERE recorded_at >= :B
      AND recorded_at < :cutoff
    GROUP BY device_id
),
history AS (
    SELECT
        device_id,
        SUM(power_sum) / NULLIF(SUM(valid_count), 0) AS historical_avg
    FROM history_parts
    GROUP BY device_id
)
SELECT r.device_id
FROM recent AS r
JOIN history AS h ON h.device_id = r.device_id
WHERE r.recent_avg >= 1.25 * h.historical_avg;
```

Devices without valid recent or historical readings remain excluded through NULL averages. The percentage interpretation assumes nonnegative historical average power.

## Numerical example: one year of growth

Suppose the table starts with 20 million rows and receives one million rows per day for 365 days. It now contains:

```text
20,000,000 + (365 * 1,000,000) = 385,000,000 raw readings
```

Assume there are 10,000 devices, arrivals are distributed evenly through each day, the summary job is current, and the query runs at noon UTC. The summary boundary `B` is yesterday at midnight, while the rolling cutoff is yesterday at noon.

| Input | Time range | Rows contributing to the calculation |
| --- | --- | ---: |
| Cumulative history summary | Before yesterday at midnight | 10,000 summary rows |
| Historical remainder | Yesterday, midnight to noon | 500,000 raw readings |
| Recent readings | Yesterday at noon to today at noon | 1,000,000 raw readings |
| Total | | 1,510,000 rows |

The original query processes approximately 385 million readings. The revised calculation consumes approximately 1.51 million raw or summary rows, about **255 times fewer input rows**, a **99.6% reduction**. 

## Compromises and operational requirements

- **Consistent summaries:** Updating the summary and advancing `B` must be atomic. The query must read the boundary, summary, and raw data from a consistent database snapshot. Retries must not add the same day twice.
- **Late arrivals and corrections:** A reading inserted or changed before `B` must also update the appropriate summary. Otherwise, the historical average becomes stale. This requires a coordinated ingestion or reconciliation process.
- **Partition maintenance:** Future daily partitions must be created in advance. Old partitions can be archived or dropped only after their contribution is safely summarized and the retention policy allows it. A bounded retention policy also prevents the number of partitions from growing indefinitely.
- **Historical detail:** Summaries preserve sums, counts, and averages, but cannot reconstruct individual readings, percentiles, or arbitrary historical windows. Those analyses require retained raw data or an archive.
- **Storage and write cost:** Indexes, summaries, and their maintenance consume storage and processing resources. Initial migration of the large table must be planned and tested separately.
- **Performance remains workload-dependent:** One to two million raw readings per query can still be expensive at high query frequency. If needed, hourly summaries could reduce this further, with raw readings retained for partial hours at the rolling boundaries.
