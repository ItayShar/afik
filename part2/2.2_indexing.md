# Indexing strategy

I created the following covering index to improve the query that compares each device's average power in the last 24 hours with its historical average:

```sql
CREATE INDEX idx_device_time_power
ON device_telemetry_logs (
    device_id,
    recorded_at,
    voltage,
    `current`
);
```

## Why I chose these columns and this order

I placed `device_id` first because the query groups readings by device using `GROUP BY device_id`. The index keeps each device's readings together, giving MySQL the option to aggregate in index order and avoid an additional sort. The actual execution plan determines whether MySQL uses this approach.

I placed `recorded_at` second because the query needs the timestamp to distinguish readings from the last 24 hours from historical readings. Within each device, the index orders readings by timestamp. This order also supports queries that filter by a specific device and a time range. For this aggregation, its main role is to supply the timestamp directly from the index; it does not let MySQL skip the historical readings.

I included `voltage` and `current` last because the query calculates power as `voltage * current`. Including both makes the index cover every column needed by the query, allowing MySQL to obtain those values from the index without looking up each corresponding table row. Their relative order does not matter for this query because neither column is used for filtering or grouping. An index containing only `device_id` and `recorded_at` would not cover the calculation.

## Measured results

I tested the query on a table containing approximately 1,000 rows, first without this index and then after creating it.

| Test | Reported execution time |
| --- | ---: |
| Before creating the index | 3.468 seconds |
| After creating the index | 1.344 seconds |

The measured execution time decreased by 2.124 seconds, or approximately **61.2%**:

```text
((3.468 - 1.344) / 3.468) * 100 ≈ 61.2%
```

It's worth mentioning that different table sizes with more entries could've resulted with a better or worse performance followed by the indexing. Since I can't fit 20 million entries on my computer, this test will have to suffice. In a production environment, more testing is required.
