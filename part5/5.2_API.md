# API & Secrets Security

The AI analysis endpoint should enforce security in backend code, with the model limited to analyzing the data it receives.

## Keep API keys outside the AI's reach

Store the AI provider's API key in a backend secret manager and let the backend attach it to the provider request. Never include keys in frontend code, prompts, system messages, model-visible tool responses, or logs. The model should have no tool that can read environment variables, secret stores, or arbitrary server files. If a backend tool needs credentials, it should use them internally and return only the required result.

## Grant minimal permissions and provide minimal data

Authenticate the user and verify their permission to analyze the requested device on every request. Perform these checks in backend code, independently of the model's decisions. For an analysis-only task, give the model no write permissions or action-taking tools; if a tool is necessary, expose only a narrowly scoped, read-only operation with server-enforced authorization. Send only the telemetry fields and time window needed for the analysis, excluding unrelated devices, personal information, credentials, and internal metadata.

## Reduce prompt injection opportunities

Allow as little user-provided free text as possible. Prefer predefined analysis options, validated device identifiers, numeric parameters, and bounded time ranges. If free text is necessary, limit its length and purpose, and treat it as untrusted data rather than instructions. Apply the same treatment to device names, telemetry labels, and other externally supplied text, since injection can arrive through those fields too. Input validation and filtering reduce exposure but cannot guarantee that prompt injection is prevented.

## Use system-role guardrails

Build the system message on the server and prevent users from supplying or overriding message roles. Use it to define the model's narrow analysis task, require it to treat embedded instructions in telemetry or user text as untrusted, and specify an expected output schema. Keep trusted instructions separate from input data, and validate the response before displaying or using it. System-role instructions are an additional guardrail, not a security boundary: access to secrets, data, and tools must remain restricted by backend controls even if the model follows a malicious instruction. Render its output safely rather than executing it or inserting it as raw HTML.

## Rate-limit requests and resource usage

Enforce per-user and per-tenant rate limits on the backend, with IP-based limits as an additional protection. Cap request size, telemetry sample count, concurrent analyses, model input/output tokens, and request duration. Apply usage or spending quotas to limit cost, and return HTTP 429 when rate limits are exceeded. Monitor unusual usage without logging secrets or unnecessary sensitive data.
